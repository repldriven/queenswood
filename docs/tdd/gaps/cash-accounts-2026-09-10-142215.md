# Cash accounts: gap analysis

Subject: [cash-accounts.md](../cash-accounts.md) — Cash accounts.

## Verdict

**Fail.**

The core the TDD is built on holds: an account is the join of a bank, a
party, a product version and one currency; `:account-type` is derived
from the party and is not a caller input; opening and closing are the
changelog-relay two-step, with the brick's own event handler gated on the
source status so redelivery is a silent no-op; every closing, rotating and
migrating write guards `:cash-account-status-opened` with
`:cash-account/invalid-status`; the SCAN number comes from a monotonic
counter that never re-issues, the BBAN is derived and unique-indexed, and
a rotation retires the old addresses on the record. The verdict fails on
what has been built around that core since the TDD was written:

- The lifecycle has a fifth state, `suspended`, that the TDD lists as a
  limitation it does not have, and no money-moving path reads the
  account's status at all — a suspended, closing or closed account can
  still be debited and credited (F1).
- The caller does not choose the product version. Opening resolves the
  version effective today, and an unknown product, a draft-only product
  and an expired one all come back as "Product is not published" (F2).
- Closing refuses a non-zero balance, holds included, and the capability
  that waives the check is granted by no shipped policy — the TDD says
  there is no check (F3).
- The sort code is minted per bank by a fountain in the bank brick, and
  the account-number fountain is the brick's own counter, not a fn the
  caller supplies — the TDD says a single hardcoded `040004` and a
  pluggable fountain (F4).
- The reads live in a second brick the TDD does not name, the file list
  is wrong, and one of the three documented lookups has no caller (F5).
- Only one count bound exists, evaluated twice; closed accounts and the
  bank's own house accounts consume it (F6).
- Every save relays a `cash-account-status-changed` event, including
  four writes that change no status (F7).
- The record, the command-reply schema and the API component have all
  drifted from the data model: the reply to an open never carries the
  BBAN (F8).
- Nothing tests the open path's idempotent replay, either count limit,
  or the query brick at all (Missing evidence).

The verdict flips to pass when the TDD defines what each status permits
and the payment path enforces it, the opening flow is rewritten around
version resolution and the per-bank sort code, the balance check and the
idempotency read-backs are documented, the Architecture names both
bricks, the reply schema is regenerated from the record, and tests reach
the open replay and a count limit.

## What matches

- An account carries `:bank-id`, `:party-id`, `:product-id`,
  `:version-id`, one `:currency`, `:product-type` snapshotted from the
  version and `:account-type` derived from the party — person to
  personal, anything else to business — with no caller override.
- `new-account` runs policy resolution, the party and product reads,
  the two counts, the capability check, the limit checks, address
  allocation, the balance-bucket writes and the account save in one
  `store/transact`, and the account lands in
  `:cash-account-status-opening`.
- `save-account` co-commits a `ChangelogEvent` envelope with every
  record write. The `cash-account-watcher` runner in
  `exclusive-dispatchers-service` republishes it to the
  `cash-accounts-event` channel, and the brick's own event processor
  in `operational-processors-service` calls
  `complete-status-transition`, which flips opening to opened and
  closing to closed, gated on the loaded status still being the source,
  and skips silently otherwise. The events test proves the replay is a
  no-op, and the API scenarios poll the real relay from `opening` to
  `opened` and from `closing` to `closed`.
- Close, suspend, rotate and migrate assert `:cash-account-status-opened`
  as the first `let-nom>` binding and reject
  `:cash-account/invalid-status` with the id, status and allowed set;
  resume asserts `suspended`; the api base maps the kind to 409.
- Capability requests are `{:action … :account-type …}` on the
  `:cash-account` kind; policies resolve by `{:bank-id}` on open and
  `{:bank-id :account-id}` afterwards, and `:policies` in `opts` skips
  the lookup.
- One Balance per `:balance-products` entry on the version, in the
  account's currency, is written before the account in the same
  transaction.
- The SCAN number is the next value of a monotonic FDB counter keyed by
  sort code, formatted to eight digits; the BBAN is
  `<sort-code><account-number>`, denormalised onto the record and held
  by the unique `CashAccount_by_bban` index; a closed account keeps its
  number, and the store test proves the next allocation differs.
- `rotate-address` draws a fresh set from the version's allowed schemes,
  rewrites `:bban`, appends the old addresses with `:retired-at` to
  `:retired-payment-addresses`, stays `opened`, and stamps the command's
  key so a retry under it allocates nothing — proven at the fountain and
  over HTTP with an injected lost reply.
- The version's `:allowed-payment-address-schemes` drives allocation;
  SCAN is the only scheme handled, and any other rejects
  `:cash-account/unsupported-scheme`.
- Every API write goes over the bus as a command; the api base requires
  only the query brick, as ADR-0017 says.
- The migration path the References cite exists, repins
  `:product-id` and `:version-id` only, and requires `opened`.

## Findings

Severity is High where a stated guarantee is broken, Medium where the
design and the code disagree in a way a reader would act on, Low where
the document is incomplete.

### F1. High — a fifth state the TDD denies, and no status stops money

The Known Limitations say "Suspension isn't a lifecycle state.
`CashAccountStatus` has no frozen/suspended state, and the policy
vocabulary (`CashAccountAction`) is just open/close." The proto carries
`CASH_ACCOUNT_STATUS_SUSPENDED`, the domain has `suspend-account` and
`resume-account` as single-phase flips between `opened` and `suspended`,
the commands are `suspend-cash-account` and `resume-cash-account`, the
routes are `/suspend` and `/resume`, the platform policy grants
`:cash-account-action-suspend` and `-resume`, and the API scenario runs
the round trip. The state diagram and the lifecycle section do not
mention it.

What the state means is defined nowhere, because nothing outside the
brick reads `:account-status`. The payment brick loads the debtor and
creditor with `get-account` on submit and settlement and checks
currency and distinctness, never status; the inbound path finds the
creditor by BBAN and credits it; the balance and transaction bricks do
not see the account. So a suspended account sends and receives
payments, nothing stops an `opening` account being debited, and a
closed account —
which keeps its `:bban` under the unique index, as the TDD says it must
— still matches an inbound payment and is credited rather than parked
in suspense. The TDD's retention argument is that recycling a number
"would risk a payment intended for the old account holder landing on
whoever gets the number next"; the payment instead lands on the closed
account. The two readers that do consult status are the interest run,
which accrues on `opened` and `suspended` alike, and the migration
verdict, which skips anything not `opened`. A suspended account also
cannot be closed: close requires `opened`, so the operator must resume
it first. Traced, not executed. Evidence: `suspend-account` and
`close-account` in the cash-account brick's `domain.clj`,
`eligible-cash-account-statuses` in the interest brick's
`domain/run.clj`, the `get-account` and `get-account-by-bban` reads in
the payment brick's `core.clj` and `events.clj`, and
[account.proto](/components/schema/resources/schemas/cash-accounts/account.proto).

Fix: add `suspended` to the diagram and the lifecycle section with both
transitions; state for each status whether it may be debited, credited,
accrue interest, be closed, rotated or migrated; put the guard where the
money moves — the payment domain reading the account's status, or a
capability the payment check evaluates — and say what an inbound to a
closed or suspended BBAN does. Add scenarios for each.

### F2. High — the version is resolved, not chosen, and unknown reads absent

The Opening flow's step 2 loads "the **product** (the published version
chosen by the caller). Refuse if missing or not published." The request
component has `party-id`, `name`, `currency` and `product-id`, the
`OpenCashAccount` Avro record has no `version_id`, and `open-account`
calls `get-product` then `active-version` for `utility/today`, so the
version is whichever published one is effective today under the
products TDD's window rule; the account records it. `get-product`
returns an empty version list for an id nobody created rather than a
not-found, so `active-version` is nil and the domain rejects
`:cash-account/open` with "Product is not published" — the same 422
for an unknown product, a product with only a draft, and a product
whose window does not contain today. The route documents a 404
`ProductNotFound` this path cannot produce and a 422
`CashAccountAlreadyExists` with type `cash-accounts/exists` that nothing
produces. `:cash-account/open` names the call site, not the problem, so
a client cannot tell the three cases apart, and
`validation/valid-product?` can never fire because `active-version` has
already filtered to published. Traced, not executed. Evidence:
`open-account` in the cash-account brick's `core.clj`,
`CreateCashAccountRequest` in the api base's cash-account
`components.clj`, `get-product` in the product query brick's `core.clj`,
and the 404 and 422 lists on the create route in `routes.clj`.

Fix: rewrite step 2 as "resolve the version effective today, refuse when
there is none", link the products TDD's effective-dating section, give
the rejection a problem name carrying the product id and the day,
distinguish an unknown product (404) from one with no active version
(422), drop the `exists` example, and delete `valid-product?` or say
what it guards.

### F3. High — close refuses a non-zero balance, and nobody holds the waiver

The Closing flow says "The current implementation does not ship a
balance-must-be-zero invariant — closing a non-empty account is a
caller-side discipline today", and the Known Limitations repeat it.
`close-account` lists the account's balances, treats any bucket whose
credit and debit differ as non-zero across every balance status — a
pending hold counts — and rejects `:cash-account/non-zero-on-close`,
mapped to 409, unless the policies grant
`:cash-account-action-close-non-zero`. The platform capabilities seed
grants open, close, suspend, resume, rotate-address and migrate; no seed
grants close-non-zero, so in a deployed system a non-zero close is
always refused and the waiver is reachable only by a test passing
`:policies`. The rejection's `:posted-balance` is the posted net, while
the check ran over holds too, so an account with a zero posted balance
and a pending outgoing hold is refused with a payload showing zero.
Nothing sweeps a residual balance. Evidence: `close-account` and
`non-zero-balances` in the cash-account brick's `domain.clj`,
[cash-accounts.yml](/components/resources/resources/policies/platform/restricted/capabilities/cash-accounts.yml)
under the platform capabilities, and the `close-account-non-zero-rejected`
API scenario.

Fix: document the invariant, that holds count, and the waiver; decide
which tier, if any, is seeded with it; report the offending buckets or
rename the payload key.

### F4. Medium — a per-bank sort code, and a fountain that is the brick's own

The SCAN section says "Queenswood uses a single configured sort code
(`040004` is the default constant in domain code)", the Known
Limitations say it is "hardcoded in `domain.clj`", the Background says
"the same sort-code spans all organisations on this clearing identity",
and the Alternatives reject "account number generation inside the
brick" in favour of a fountain "passed in by the caller" that the brick
"doesn't second-guess". The bank brick's `allocate-sort-code` mints a
six-digit `00`-prefixed sort code per bank from a global counter at bank
creation and stores it on the bank record; the api base's open handler
reads the bank and puts `:sort-code` on the command; the domain rejects
`:cash-account/missing-sort-code` without one; a rotation re-derives the
sort code from the account's existing SCAN address. The account-number
fountain is `store/allocate-payment-address`, a counter keyed by sort
code inside the cash-accounts store, and the interface takes no fountain
argument — the "pluggable fn" is a closure `core.clj` builds over its
own store. The TDD's own "Number retirement" paragraph already describes
that counter, so the document contradicts itself. `040004` survives only
as example data in the api base and the adapters and in one domain test.
Evidence: `allocate-sort-code` in the bank brick's `store.clj`,
`open-cash-account` in the api base's cash-account `commands.clj`,
`allocate-payment-address` in the cash-account brick's `store.clj`, and
the `sort-code-fountain` scenario under `banks`.

Fix: rewrite SCAN generation around the per-bank sort code carried on
the open command and the brick's per-sort-code counter, note the `00`
range, and delete the two alternatives and the two limitations that
describe a design the code does not have.

### F5. Medium — the Architecture names one brick, and the file list is wrong

The TDD names `domain.clj`, `store.clj`, `core.clj` ("orchestration of
open, get, list"), `commands.clj`, `events.clj`, `validation.clj`
("Malli schemas for incoming data") and `system.clj`. Every read —
`get-account` with optional balance and transaction embeds,
`get-accounts` paged by cursor, `get-account-by-bban`,
`find-account-by-product`, `find-account`,
`find-account-by-idempotency-key`, `find-accounts-by-party`,
`count-by-org`, `count-by-version`,
`count-by-org-product-account-type-currency` and
`reduce-accounts-with-balances` — lives in `cash-account-query` under
ADR-0017, which the TDD does not cite; the write brick requires it
inside its transactions and the api base requires only it. The write
brick also has `changelog.clj`, which builds the envelope and loads the
Avro schema off the classpath, unlisted. `validation.clj` holds no
Malli: it is three predicates that produce rejections —
`valid-product?`, `valid-currency?`, `valid-party?` — which is
`error/reject` outside `domain.clj`, and one of them mints
`:cash-account-product/not-published` in another brick's namespace.
`core.clj` has no get or list. `find-account-by-product`, one of the
TDD's three lookups, has no caller anywhere. The
`migrate-cash-account-product` command has a handler and a registered
schema and no dispatcher — the migration brick calls `migrate-account`
in-process. Both bricks still say `bank-cash-account`,
`bank-cash-account-query`, `bank-api`, `bank-party` and `bank-bank`;
the query interface cites a "status-transition watcher" that no longer
exists; the api base's `PaymentAddress` docstring cites a
`payment-address->avro` that exists nowhere; and the TDD's References
end with "`cash-account` brick interface", singular. Evidence:
`validation.clj` and `changelog.clj` in the write brick, the query
brick's `interface.clj`, and `command-handlers` in the write brick's
`commands.clj`.

Fix: list both bricks and their files and cite ADR-0017; move the three
checks into `domain.clj` and rename the not-published kind under
`:cash-account/`; delete `find-account-by-product` or name its caller;
delete the migrate command or give it a route; fix the names.

### F6. Medium — one bound, checked twice, filled by closed and house accounts

Step 6 lists two checks: a per-organisation total ("at most 100,000
accounts") and a per-(org, product-type, account-type, currency)
combination ("at most 10 personal GBP current accounts per org"). Both
checks exist — `check-total-limit` and `check-subtotal-limit`, each
sending `{:aggregate :count :window :time-window-instant}` with the
subtotal adding the three filter keys — but the shipped limits are one
unfiltered `cash-account` count per tier: 1,000,000 on the platform,
50 on micro. The policy matcher applies an unfiltered limit to any
request, so the subtotal check re-tests the same ceiling against a
smaller number and can never bind; no seed carries a
`CashAccountLimitFilter`, although the proto supports product type,
account type and currency and the products seeds do filter by type. The
two count indexes have no status term, so a closed account consumes the
cap forever, and the bank's house accounts — one per currency, opened
through `new-account` at bank creation under the bank's own org party
and the internal own-funds product — count too: a micro bank with one
currency starts at one of fifty. Evidence: `check-subtotal-limit` in the
write brick's `domain.clj`, `matches?` in the policy brick's
`match.clj`,
[cash-accounts.yml](/components/resources/resources/policies/micro/restricted/limits/cash-accounts.yml)
under the micro limits, the `cash-accounts` indexes in
[fdb-record-types.yml](/components/resources/resources/system/fdb-record-types.yml),
and `new-house-account` in the bank brick's `core.clj`.

Fix: state the bounds and window that ship, say a filtered limit is what
gives the second check a bound and seed one or drop the example, and
decide whether closed and internal accounts count.

### F7. Medium — every save relays a status-changed event, changed or not

The Rotation paragraph says "Single-phase, no event leg", and the
changelog pattern is described for open and close only. `save-account`
co-commits a `cash-account-status-changed` envelope on every write:
suspend (opened to suspended), resume (suspended to opened), rotation
(opened to opened) and migration (opened to opened, deliberately —
`migrate-account`'s docstring says a reader tailing the changelog needs
to see it). The relay republishes each to the event channel and the
brick's handler acts only when `:status-after` is opening or closing,
dropping the rest. So the bus carries an event named for a status
change on four writes that change none, a rotation and a migration are
indistinguishable on the wire, and the envelope's `dedup_key` —
`<account-id>:<status-after>` — is the same string for the open's
terminal leg, every rotation, every migration and every resume, and a
second suspension repeats the first's. That is harmless today because
the relay passes `:deduplicate? false` and consumers key on
`event_id`, but the field the envelope offers for deduplication does
not identify a write. Evidence:
`save-account` in the write brick's `store.clj`, `status-changed` in its
`changelog.clj`, `complete-status-transition` in its `core.clj`, and
`migrate-account`'s docstring.

Fix: say that every save writes an entry and which the handler ignores;
carry a change kind in the payload or the event name so a consumer can
tell a rotation from a migration; give the dedup key a per-write
component.

### F8. Medium — the record, the reply schema and the API component differ

The data-model block omits `:idempotency-key` (tag 21, unique per bank),
`:retired-payment-addresses` (tag 23, mentioned only under Rotation),
`:last-rotation-idempotency-key` (tag 24) and `:gl-control-account-id`
(tag 20). The proto's comment on tag 20 says it is "resolved at
open-time by chasing product-type → control gl-code"; nothing sets it,
the chart-of-accounts TDD says "There is no `gl_control_account_id`",
and `pb->CashAccount` strips it as an empty string — a dead field with a
misleading comment. The Avro `cash-account` record every command reply
is serialised through has no `bban`, no `retired_payment_addresses` and
no idempotency fields, and carries `gl_code`, `gl_account_type`,
`gl_account_class`, `required` and `gl_control_code`, which the proto no
longer has since ledger accounts became their own record type. So the
reply to open, close, suspend, resume and rotate never carries the BBAN,
although the API component declares `bban` optional, and a client learns
it only from a GET; the retired addresses appear on no route at all.
The API component declares `gl-code`, and the read routes return the
proto map unfiltered with extra keys kept, so `idempotency-key` and
`last-rotation-idempotency-key` reach GET bodies undocumented. Traced,
not executed. Evidence:
[account.proto](/components/schema/resources/schemas/cash-accounts/account.proto),
[account.avsc.json](/components/schema/resources/schemas/cash-accounts/account.avsc.json),
`CashAccount` in the api base's cash-account `components.clj`, and
`->response` in the write brick's `commands.clj`.

Fix: complete the data-model block, delete the dead proto field and its
comment, regenerate the reply schema from the record — add `bban` and
the retired addresses, drop the GL fields — and decide whether the two
keys are exposed.

### F9. Medium — the open path's idempotency is undocumented

The TDD says nothing about idempotency. The command envelope's id — the
`Idempotency-Key` header — is stamped onto the account and held by the
unique `CashAccount_by_idempotency_key` index; `or-already-opened`
catches the uniqueness violation and returns the account the key
already opened, which is what answers a retry whose first reply was
lost after the API's own cache missed it. It does so outside
`store/transact`, against the caller's handle: with a config, the
command path, that is a fresh transaction and works; with a live
transaction — the bank brick opens its house accounts inside its own
creation transaction — the violation would surface at the outer commit,
past the read-back, though that path passes no key today. Close,
suspend and resume stamp nothing, so a retry after a lost reply meets
`:cash-account/invalid-status` and a 409 where the first reply was a
200. Traced, not executed. Evidence: `or-already-opened` in the write
brick's `core.clj`, `dispatch` in its `commands.clj`, the
`rotate-address-lost-reply` API scenario, and the idempotency TDD.

Fix: add an Idempotency section naming which writes stamp a key and
which read back, and that a lost-reply retry of close, suspend or resume
is a 409; move the read-back inside the transaction or say it needs a
config.

### F10. Low — the opening flow's order and side details differ

The party is loaded before the product, not after, and a missing party
is `:party/not-found`; the sort-code check precedes every other; the
currency check treats an empty `:allowed-currencies` as unrestricted;
`opening-balances` falls back to one default posted bucket when the
version declares none; the balances are written before the account.
The bank has accounts of its own: `new-house-account` creates and
publishes an own-funds product per currency and opens an account under
the bank's org party through the same path, under the platform policies,
and it sits in `opening` until the relay flips it — the "Connection to
balances" section does not say so. Evidence: `open-account` in the
write brick's `core.clj`, `opening-balances` in its `domain.clj`, and
`new-house-account` in the bank brick's `core.clj`.

Fix: reorder the steps, add the fallback bucket, and describe the house
accounts.

### F11. Low — the Lookups section is out of date

`get-account` enriches with balances and transactions on request;
`get-accounts` pages by cursor, one hundred by default;
`get-account-by-bban` is not scoped to a bank and is also called by the
ClearBank adapter's Confirmation of Payee handler, not only the
payment-event processor; `find-account-by-product` is dead (F5); the
party brick's close guard uses `find-accounts-by-party`, filtered to the
bank in memory over a party index; interest and migration stream a bank
with `reduce-accounts-with-balances`, a merged scan of two stores that
is not a consistent snapshot; `count-by-version` sizes a migration's
cohort. On the API, the GET handler's plural `cash-accounts/not-found`
branch is unreachable because `get-account` rejects rather than
returning nil, so the live type is `:cash-account/not-found` while the
documented example is the plural; the other examples mix colon-prefixed
and bare types and name `cash-account/product-not-published` for a kind
the brick emits as `:cash-account-product/not-published`. Evidence: the
query brick's `interface.clj`, `get-cash-account` in the api base's
cash-account `queries.clj`, and its `examples.clj`.

Fix: rewrite Lookups around the query brick's surface and its callers,
delete the dead branch, and make the examples match the kinds.

### F12. Low — the Known Limitations and the PRD are largely stale

Suspension (F1), the balance check (F3), the sort code and the fountain
(F4) are false, and the policy vocabulary has seven actions — open,
close, suspend, resume, close-non-zero, rotate-address, migrate. No
re-open, the rigid derivation, no party re-validation, no dormant flow
and SCAN-only remain true; the proto reserves tag 22 for a last-activity
timestamp nothing writes. The PRD lists suspension and a
balance-zero check as non-goals, says every SCAN address shares one
sort code, promises tenants a lookup by payment address that has no
route, and does not mention migration; its account of rotation is
right. Evidence: [cash-accounts.md](../../prd/cash-accounts.md) and
`CashAccountAction` in
[policy.proto](/components/schema/resources/schemas/policies/policy.proto).

Fix: rewrite the limitations to the five that hold, and reconcile the
PRD's non-goals and open questions with F1, F3, F4 and the migration
path.

## Missing evidence

- No test opens twice under one key. The store test proves the unique
  index and the read-back primitive; nothing drives `or-already-opened`
  end to end, and no API scenario replays an open.
- No test reaches either count limit, and the subtotal has no bound to
  reach (F6).
- `:cash-account/no-payment-schemes` and `:cash-account/unsupported-scheme`
  have no test. The validation test's docstring says they and the
  not-found cases are covered "in interface_test.clj"; that file holds
  the rotation retry and nothing else.
- `cash-account-query` has no tests. The BBAN index, the party lookup,
  `count-by-version` and the merged scan's semantics — page sizes, an
  account with no balances, rows from another bank — are exercised only
  through their callers' scenarios.
- `commands.clj` has no dispatch test, unlike the bank, party and
  interest bricks; nothing asserts the command names reach the right
  fns or that the envelope id becomes `:idempotency-key`.
- No test shows what a suspended, closing or closed account can do,
  because nothing refuses it (F1): no scenario pays from or to one, and
  none sends an inbound to a closed BBAN.
- No API scenario opens against an inactive party, a currency the
  version does not allow, or an unknown product id, so the three
  rejections and the collapsed message in F2 are unproven over HTTP.
- The domain scenario runner flips accounts with the seed shortcuts and
  wires no relay; the property model excludes `open-account` outright,
  knows only open and closed, and its projection would throw on a
  suspended account.
- No test grants `close-non-zero` through a policy record rather than a
  `:policies` override (F3).

## Recommended fixes

In order:

1. Define the status semantics and enforce them in the payment path;
   add `suspended` to the lifecycle and the diagram; say what an inbound
   to a closed BBAN does (F1).
2. Rewrite the Opening flow around today's active version, the per-bank
   sort code and the balance check on close; name the rejections for
   their problems and fix the route documentation (F2, F3, F4, F10).
3. Name both bricks and the changelog file, cite ADR-0017, move the
   validation predicates into `domain.clj`, and remove the dead lookup,
   the dead command and the stale names (F5, F11).
4. Document the limits that ship and seed a filtered one or drop the
   example; decide whether closed and house accounts count (F6).
5. Document the changelog entry every save writes and give the dedup key
   a per-write component (F7); complete the data model, delete the dead
   proto field and regenerate the reply schema (F8); add the Idempotency
   section (F9).
6. Rewrite the Known Limitations and reconcile the PRD (F12).
7. Add tests: an open replayed under one key, a count limit reached, the
   two scheme rejections, a query-brick suite, a command dispatch test,
   and scenarios for payments against each non-opened status.
